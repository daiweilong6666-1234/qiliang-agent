================================================================
一、推演主题与核心问题
================================================================

本次推演围绕一个核心矛盾展开：

  传统 PRD 用"体验流畅""生成爆款""确保合规"等模糊词汇——
  导致 AI 辅助编程 (Vibe Coding) 产生严重幻觉和偏离。
  如何在 PRD 中用结构化、数据化的语言定义验收标准，
  让执行者能把 AC 直接翻译成 if-else + 正则 + 重试上限，
  中间没有任何一句需要向 PM 打电话确认？

  推演以 Phase 2 翻译后安全扫描为具体案例，
  通过逐轮决策，最终产出一份 6 条完整的验收标准（AC-SEC-01 ~ AC-SEC-06）。


================================================================
二、推演路径回顾（逐轮决策）
================================================================

【第 1 轮】验收标准的基准：什么是"能写代码的 AC"
----------------------------------------------------------------
Tech Lead 切入角度：
  展示三段 PRD 写法对比——
    PRD A："确保输出内容具备 TikTok 爆款潜质，节奏紧凑、钩子有力"
      → 无法翻译成代码。"爆款潜质"没有量化标准。
    PRD B："输出 3-5 条钩子句，每条具备吸引力"
      → "吸引力"谁来判？改 temperature 还是改 Prompt？
    PRD C："hook_sentences[] 每条 ≤ 18 字，且须包含三类之一：
            ①数字型 ②反常识型 ③身份标签型。不满足打回，最多重试 3 次"
      → 正则可校验，三类有可枚举关键词库，重试有上限。直接可写代码。

灵魂拷问：
  Phase 2 翻译后安全扫描的验收标准怎么写？
  如果写成"翻译结果应符合 TikTok 社区规范"——工程师不知道
  校验对象是什么、校验方式是什么、通过条件是什么、失败后触发什么。

PM 回应：今天的目标就是写出 Phase 2 安全扫描的 AC。

Tech Lead 指出：AC 不是代码，是"在什么条件下通过、不通过、重做"。
  拆成 6 个决策点，一次一个。


【第 2 轮】决策点 1：扫描覆盖范围
----------------------------------------------------------------
Tech Lead 问题：
  安全扫描在 translated_script 里找什么？
  A：只找违禁词 Excel（精确匹配）
  B：违禁词 + 疑似违规语义（语义匹配兜底）
  C：违禁词 + 语义违规 + 商业夸大（最安全但每条多一次 LLM）

PM 选择：B。
  理由：
    A → 风险大，TikTok 本身用的是语义算法
    C → Token 成本太高
    B → 精确匹配做第一道筛，语义做第二道兜底，成本可控


【第 3 轮】决策点 2：LLM 语义判断的触发条件
----------------------------------------------------------------
Tech Lead 问题：
  每条 translated_script 都要过 LLM 还是只在"可疑"时过？
  方案 1：Excel 命中就送 LLM
  方案 2：Excel 命中 + 命中词周围 ±15 词有可疑邻近词才送 LLM

PM 选择：方案 2。
  理由：避免每条含普通关键词（如 "Muslim"）的脚本都触发
  一次 LLM 调用。加一层规则过滤降低 Token 消耗。


【第 4 轮】决策点 3：LLM 判断后的处理方式
----------------------------------------------------------------
Tech Lead 问题：
  LLM 说"违规"时怎么处理？LLM 说"不违规"时怎么处理？
  A：违规自动拦截 / 不违规直接放行
  B：违规自动拦截 / 不违规人工看一眼
  C：违规人工确认再拦截 / 不违规直接放行
  D：违规自动拦截 / 不违规直接放行（同 A）

PM 选择：B —— 不论 LLM 判什么，都让人工看一眼。
  理由：
    LLM 可能误判（把反歧视论述判成违规）→ 好内容被错杀
    LLM 可能漏判（把擦边违规判成安全）→ 隐患放行
    V1.0 每天仅 1-2 条触发 LLM，每条 30 秒，扛得住


【第 5 轮】决策点 4：人工判定违规后的处理
----------------------------------------------------------------
Tech Lead 问题：
  运营看完，判定"LLM 说得对，这条确实违规"——接下来怎么办？
  A：直接丢弃（少一个测试样本）
  B：打回 Phase 1，换模板重生成
  C：打回 Phase 1，换模板 + 加负面约束塞进 Prompt

PM 选择：C。

Tech Lead 追问三个数字：
  重试上限几次？触达上限后该脚本怎么办？触达上限后该书怎么办？


【第 6 轮】决策点 5：重试上限和降级出口
----------------------------------------------------------------
PM 决策：
  - 单条脚本违规重试上限：3 次
  - 触达上限后该脚本：移交人工手动优化
  - 触达上限后该书：不暂停，继续生成其他角度
  - PM 收到通知：重新审视「讲什么」库中该书的 unsuitable_angles

Tech Lead 收敛：
  六轮决策完毕。将所有决策翻译为 6 条工程可执行的验收标准。


================================================================
三、核心产出：Phase 2 安全扫描 AC-SEC-01 ~ 06
================================================================

AC-SEC-01：违禁词精确匹配
  输入：Phase 2 翻译通道输出的 translated_script（纯文本，英文）
  校验对象：PM 手动维护的违禁词 Excel（路径：/config/banned_terms.csv）
  匹配方式：大小写不敏感精确匹配 + 词边界匹配
  输出：命中词列表 [{term, position}]
  通过条件：命中词列表为空
  不通过：进入 AC-SEC-02

AC-SEC-02：可疑邻近词检查
  触发条件：AC-SEC-01 命中词列表非空
  扫描范围：每个命中词 position ± 15 个词
  比对目标：PM 手动维护的可疑邻近词清单（路径：/config/risky_proximity.csv）
  输出：可疑邻近词命中列表 [{term, nearby_term, distance}]
  通过条件：可疑邻近词命中列表为空 → 直接放行，不进 LLM
  不通过：进入 AC-SEC-03

AC-SEC-03：LLM 语义判断
  触发条件：AC-SEC-02 可疑邻近词命中列表非空
  输入：translated_script 全文 + AC-SEC-01 命中词列表 + AC-SEC-02 可疑邻近词列表
  LLM 任务：判断原文在上下文中是否构成 TikTok 社区规范违规
  输出格式：{violation: true|false, confidence: 0-100, evidence: [原文引用×3段]}
  通过条件：violation=false（不论 LLM 判什么，都进 AC-SEC-04）

AC-SEC-04：人工最终审核
  触发条件：AC-SEC-03 已执行（无论 LLM 结果如何）
  审核人：运营人员
  审核内容：translated_script 全文 + LLM 判断结果 + LLM 引用的三段原文证据
  审核动作：
    ① 运营判定"安全"→ 放行，脚本进入 Phase 3
    ② 运营判定"违规"→ 进入 AC-SEC-05

AC-SEC-05：违规重生成
  触发条件：运营判定违规
  动作：打回 Phase 1
    - 保留原「讲什么」锚点
    - 换一个「怎么讲」模板（排除本次使用的模板）
    - 在 Prompt 中注入运营手写的负面约束（如"Avoid mentioning religion"）
  重试上限：3 次
  重试计数：per 脚本维度（同一 translated_script 的重生成次数）
  触达上限后：
    - 该脚本移交人工手动优化（不依赖 LLM）
    - 该书不暂停，继续生成其他角度
    - PM 收到通知：该书某个角度触达 3 次违规重试 → 重新审视
      「讲什么」库中该书的 unsuitable_angles 是否需要补充

AC-SEC-06：全量安全审核（兜底）
  在 AC-SEC-01 至 AC-SEC-05 之外：
    运营每天对当天全部产出（~15 条）的 translated_script 逐条扫一眼
    耗时：15 × 30 秒 = 7.5 分钟
    发现漏网（Excel 未命中但运营判断违规）：
      ① 该词加入违禁词 Excel
      ② 该脚本打回 AC-SEC-05 流程

工程师视角：AC 到 代码 的直接映射 ─────────────────
  AC-SEC-01 → for term in banned_terms: if re.search(r'\b'+term+r'\b', text, re.IGNORECASE)
  AC-SEC-02 → text.split()[pos-15:pos+15] 与 risky_proximity 取交集
  AC-SEC-03 → DeepSeek, temperature=0.1, system prompt=仅判断违规，JSON 输出
  AC-SEC-04 → Streamlit 渲染审核卡片，两个按钮（放行/违规）
  AC-SEC-05 → retry_count++，if retry_count>=3: reroute_to_manual()
  AC-SEC-06 → Streamlit 列表页，translated_script 平铺，运营滚轮扫
──────────────────────────────────────────────────


================================================================
四、核心结论
================================================================

1. PRD 的验收标准是给执行者（人或 AI）的"代码生成指令"
   → 模糊词汇 → 幻觉代码 → 上线炸了 PM 说"你没理解我"
   → 结构化 AC → 直接翻译 if-else → 零沟通成本

2. PM 不需要懂技术实现，但必须能做决策
   → 扫描覆盖范围（A/B/C）、触发条件（方案1/2）、
     处理方式（A/B/C/D）、重试上限——都是产品决策，不是技术决策
   → 工程师不能替 PM 选，因为这些是风险评估和资源分配

3. 每个决策点都是一次"风险 vs 成本"的取舍
   → 选 B 不是选 A → 多花 LLM Token，但减少漏网风险
   → 选人工兜底不是自动放行 → 多花运营时间，但减少误杀和漏判
   → PM 的价值是把取舍理由写清楚，让执行者知道"为什么这样设计"

4. 重试上限是防止死循环的硬刹车
   → 没有上限的"打回重生成" → LLM 在同一坑反复跌倒，Token 白白烧
   → 3 次后移交人工 → 不是放弃，是换策略

5. 全量人工兜底（AC-SEC-06）在 V1.0 量级下完全可行
   → 15 条 × 30 秒 = 7.5 分钟/天
   → 而且是发现漏网、更新违禁词 Excel 的正反馈入口

6. 这份 AC 的价值不仅在于"能写代码"
   → 更在于：三个月后你回来读，你能清楚地看到
     "当时为什么这样设计"、"每个阈值的判断依据是什么"


================================================================
五、PRD 验收标准撰写方法论
================================================================

好的 AC 必须回答以下六个问题（缺一不可）：

  ① 校验对象：具体是什么数据？（哪个字段、哪个文件、哪个输出）
  ② 校验方式：精确匹配？正则？LLM 判断？人工判断？
  ③ 通过条件：什么情况下算"过了"？
  ④ 失败动作：没过的话触发什么？（打回、丢弃、熔断、告警）
  ⑤ 重试上限：可以重试几次？触达上限后降级到哪里？
  ⑥ 输入来源：校验依赖的外部数据在哪里？谁维护？

反例对照：
  ┌─────────────────────────────────────────────────────────┐
  │ ✗ "翻译结果应符合 TikTok 社区规范，避免违规内容"          │
  │   → 6 个问题一个都没回答，无法写代码                      │
  │                                                         │
  │ ✓ AC-SEC-01 ~ 06                                        │
  │   → 6 个问题全部回答，可直接翻译为 if-else + 正则 + 重试   │
  │   → 不需要向 PM 打一个电话                                │
  └─────────────────────────────────────────────────────────┘


================================================================
附：推演方法论
================================================================

本次推演采用"逐决策点拆解 + 收敛归档"方法：
  - Tech Lead 不替 PM 做决策，但把所有模糊问题拆成具体选项
  - PM 每次只需要回答 A/B/C 或填一个数字
  - 六轮决策完成后，Tech Lead 把所有决策翻译为结构化 AC
  - PM 验证：这份 AC 是否完全表达了自己的意图

本次与前面五个阶段的关联：
  - P3 定义了安全合规的分层拦截策略（战略层）
  - P4 定义了双 RAG 库 + 上下游联动（工作流层）
  - P5 把安全层从五层自动闭环砍到静态 Excel + 人工兜底（MVP 裁剪层）
  - P6 把 P5 砍剩的安全层写成了机器可读的 AC（PRD 交付层）
