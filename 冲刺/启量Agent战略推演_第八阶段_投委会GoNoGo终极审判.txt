一、推演主题与核心问题
================================================================

本次推演是第一阶段（产品定位与 0-1 基建）的最后一道关卡。

推演方法：事前验尸 (Pre-mortem)
  假设项目在未来 30 天内彻底失败（流产或被 TikTok 团灭），
  倒推最可能的死因——找出 PRD 里至今未被发现的逻辑裂缝。
  如果死因能被识别且有可行的早期预警指标，项目通过。
  如果死因无法被识别或无法预警，项目搁置。

投委会立场：
  任何伟大的设想都会死于执行。
  历史上每一艘沉没的船，下水之前都通过了全部质检。
  设计自洽 ≠ 运行安全。


================================================================
二、事前验尸路径回顾
================================================================

【第 1 轮】死因推演：RAG 反馈闭环的因果倒置
----------------------------------------------------------------
投委会主席切入角度：
  P1-P7 的推演全部通过，全链路审计残留风险为零。
  但有一个从第一天就未被挑战的前提假设：

  "用户下单是因为这条视频说服了他。"

  如果这个假设不成立——
  用户本来就打算买，视频只是凑巧出现在付款前 5 分钟。

  后果链：
    这条巧合脚本被采回 RAG → 标记为"转化型爆款"
    → 明天 LLM 用这个模板生成 15 条
    → 15 条推给真正的陌生人 → 0 转化
    → 因为你复制了一个运气的产物，不是一个可重复的说服模式

  这种"转化 = 说服力 + 运气 + 用户本来就要买的概率"的混淆，
  导致的后果是：
    RAG 库里全是随机噪声。
    真的稀缺模板因为短期没出单被三次即弃扔掉。
    运气模板被当宝贝供着。
    生成的脚本越来越散，转化率持续下滑。
    老板说"AI 没用"。项目叫停。

  死因定位：
    不是被封号，不是 LLM 幻觉，不是老板绕过加密阀门。
    是 RAG 学习系统被低样本量噪声污染——
    从"优化引擎"降级为"迷信引擎"。

投委会拷问 1：
  盯哪一个数字能最早发现"RAG 正在被噪声污染"？

PM 回答：
  看转化。转化低说明脚本没有说服力。


【第 2 轮】追一刀：转化低是结果，不是预警
----------------------------------------------------------------
投委会主席追一层：
  两条脚本对比：

  | | 脚本 A | 脚本 B |
  |--|--------|--------|
  | 播放量 | 800 | 6,200 |
  | 完播率 | 28% | 41% |
  | 订单数 | 4 单 | 0 单 |

  按现有规则：A 是转化型爆款 → 采回 RAG。B 是废物 → 三次即弃。

  但 800 播放 4 单的 0.5% 转化率——
  这 4 个人是谁？是刚好在搜这本书的人，还是完全陌生的人被说服了？
  800 播放的样本量，4 单是真实的信号还是运气？

  B 的 6200 播放 0 单——但那 6200 人里可能有 100 个人记住了书名，
  第二天去亚马逊买了。TikTok Shop 归因永远不会告诉你这件事。
  一个可能真正有说服力的脚本被扔掉了。

  核心矛盾：
    订单 ≠ 说服力。订单 = 说服力 + 运气 + 用户本来就打算买的概率。
    不能用还没被确认是噪声还是信号的数据作为判断标准。
    需要一个跟转化无关的、纯统计层面的入库门槛——最小样本量。

投委会拷问 2：
  最小播放量阈值是多少？
  低于这个播放量的脚本，哪怕出 5 单也不采。
  因为样本量不足以排除运气。


【第 3 轮】终局：统计显著性门槛
----------------------------------------------------------------
PM 最终决策：

  播放量 ≥ 5000 + 有出单 → 才有资格进入「怎么讲」RAG

  这意味着：
    - 800 播放 4 单的运气脚本 → 拒。样本太小。
    - 6200 播放 0 单的潜在说服型脚本 → 拒。无人用钱投票。
    - 5000+ 播放 + 出单 → 收。样本量排除纯随机 + 购买行为真实信号。

  唯一监控指标：
    「RAG 入库模板的平均播放量」

  预警阈值：
    该指标连续两周 < 5000 → 运营在饥不择食地往里塞低样本噪声
    → 手动暂停 RAG 反馈回路
    → PM 逐条翻阅最近入库的模板
    → 确认是运气还是说服力在驱动

================================================================
附：事前验尸方法论
================================================================

Pre-mortem（事前验尸）：
  假设项目已经失败，倒推最可能的死因。
  与传统风险评估的区别：
    - 风险评估问："可能会出什么问题？"→ 列出所有可能性
    - 事前验尸问："如果它已经死了，是什么杀死了它？"→ 找出唯一致命伤

本阶段事前验尸的发现：
  最隐蔽的死因不是"被封号"、"幻觉"、"老板干涉"——
  是 RAG 学习系统被低样本量噪声污染。

  因为噪声看起来像信号，它不会触发任何告警。
  它不会报错，不会熔断，不会被安全扫描拦截。
  它只是安静地把你的优化引擎变成迷信引擎——
  你唯一能发现它的方式，是盯住入库模板的最小样本量。

  这个漏洞之所以在 P1-P7 的七层推演中都未被触达，
  是因为它不在任何单一模块的边界内——
  它是 RAG 反馈闭环和 TikTok 流量分配随机性之间的交叉产物。
  交叉点的漏洞，只有站在全链路的角度才能看到。
