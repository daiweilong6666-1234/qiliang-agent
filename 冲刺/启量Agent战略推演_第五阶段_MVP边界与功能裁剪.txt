角色：铁血敏捷产品总监（极度厌恶臃肿功能，崇尚极简交付）

================================================================
一、推演主题与核心问题
================================================================

本次推演围绕一个核心矛盾展开：

  四阶段推演（P1-P4）产出了完整的系统架构蓝图——
  但 V1.0 MVP 到底需要其中的哪些功能？哪些是"验证核心假设必须的"？
  哪些是"看似高端但完全拖慢交付节奏的伪需求"？

  核心假设：深度理解投喂 LLM → 产出有转化的内容
  MVP 的唯一目标：用最少的代码验证这个假设

  推演用逐刀砍功能的方式，把 V1.0 PRD 从"全能胖子"削成"最小骨架"。


================================================================
二、推演路径回顾（逐轮攻防）
================================================================

【第 1 刀】砍 Phase 4 全自动后期装配流水线
----------------------------------------------------------------
总监切入角度：
  Phase 4（BGM推荐 + 转场方案 + 关键帧 + 调色预设 + 剪映JSON）
  不验证任何战略假设。核心假设在 Phase 3 产出 TTS 音频 +
  图片/视频素材的那一刻已经被验证了。Phase 4 是锦上添花，不是 MVP。

  四条砍掉理由：
  1. 不验证核心假设
  2. 工程复杂度最高、交付风险最大
  3. 剪映私有 JSON 格式随时可能被更新打破
  4. 实习生用剪映 5 分钟能干完的事，不值得四周开发

PM 反击（部分成立）：
  画面和文案的时间轴对齐必须机器做（毫秒级精度人工做不了），
  BGM、关键帧、调色等创意层可以人工。

最终裁决：
  Phase 4 瘦身为「时间轴自动对齐 + 字幕生成」，其余人工 SOP。
  BGM 和关键帧 → 运营用剪映手动加。


【第 2 刀】砍违禁词 RAG 五层自动闭环系统
----------------------------------------------------------------
总监切入角度：
  V1.0 每天产出 10-15 条，不是 405 条。
  五层闭环的信号采集层依赖"已有足够多视频被 shadow ban"，
  MVP 总共发不到 100 条，样本量养不活飞轮。
  安全是上线条件，不是验证目标。

PM 澄清：
  信息采集层指的是 changedetection.io 截图对比 TikTok 官方规范页
  → LLM 拆解 → 违禁词入库。这是零代码工具，不是需要开发的工程模块。

PM 方案：
  每天生成的视频全量人工校验（15 条 × 30 秒 = 7 分半），
  主要看前面采集层采集到的违规词。

总监追问 MVP 违禁词清单怎么来：
  A：PM 花一小时手搓一份 80-120 词条的 Excel + 每月更新
  B：开发简化版信息采集层

PM 选择：A + changedetection.io 保留。
  信息采集层 = changedetection + LLM 拆解，保留在 Layer 0。


【第 3 刀】砍加密硬阀门系统
----------------------------------------------------------------
总监切入角度：
  V1.0 没有"老板"。3 本书 × 5 个测试号，
  运营团队 = PM + 一个实习生。老板不会盯着一套还在验证核心假设
  的测试管线要求"一键铺量"。

  加密基础设施是沉没成本，写错一个字节整条管线锁死。
  门房一体的前提是"房子值钱了"——先盖房子再焊门。

总监追问 V1.0 的 RAG 入库如何管控：
  PM 请求思路指导。

总监给出 MVP 级零代码方案 —— Git PR review SOP：

  权限控制：RAG JSON 文件放在本地 Git 仓库，只有 PM 有 push 权限。
  校验流程：
    ① 修改 JSON → ② git diff 自检 → ③ 提交 PR + 描述变更内容
    → ④ PM 扫一眼 PR diff，确认无重复/无篡改 → ⑤ PM merge 生效

  为什么够用：
    - 防外来者：Git push 权限只在 PM 手里
    - 防手滑：PR diff 强制再看一眼
    - 防重复：几十条模板人脑比 Embedding 快
    - 防篡改：diff 里任何异常修改一眼可见
    - 审计追溯：commit 记录完整

  升级触发条件（三个缺一不可）：
    团队超过 3 人 AND 日产超过 50 条 AND 老板开始问"为什么不能一键铺量"

PM 确认接受。


【第 4 刀】砍 Embedding 语义指纹去重管线
----------------------------------------------------------------
总监切入角度：
  V1.0 每天产 15 条，人眼 60 秒平铺扫一遍比 Embedding 更准更快。
  Embedding 模型选型、部署、调阈值的时间够人肉审三个月。
  打回重生成的根因是 Prompt 设计不是缺少去重管线。

总监追问触发条件：
  PM 给出：日产 ≥ 50 条时加上 Embedding 去重管线。

最终裁决：
  V1.0 砍掉，日产 < 50 条之前不写一行去重代码。
  日产 ≥ 50 条时激活该模块。

总监追问人肉去重 SOP：
  运营每次 LLM 批量生成完后，15 条脚本平铺同一窗口，
  60 秒扫一遍。发现两条意思撞了 → 标黄 → 手动选一条，
  换一个「怎么讲」模板重新生成。


【第 5 刀】砍 TikTok 数据自动采集 + 评论语义聚类
----------------------------------------------------------------
总监切入角度：
  V1.0 总共发不到 100 条，评论可能 30 条不到。
  30 条评论不够喂聚类算法。
  人手动截图粘贴到 Notion 花 3 分钟总结更有效。

总监追问：数据闭环最简替代方案是什么？

PM 回答：
  不可能要评论区爬取功能的。人工看一眼评论区，
  把人的理解直接投喂给 LLM。

最终裁决：
  砍掉 TikTok API 自动采集 + 评论聚类算法。
  评论区数据 → 运营人工扫一眼 → 把有价值的反馈直接写成
  深度理解投喂到「讲什么」库。这是"数据闭环"，不是"数据看板"。


【第 6 刀】砍 FastAPI 后端层
----------------------------------------------------------------
总监切入角度：
  V1.0 单机 Streamlit 直接 import JSON / ORM 直接读写 MySQL 就够了。
  FastAPI 是给多服务通信用的，MVP 不存在这个场景。

PM 反击（成立）：
  数据库保留。就算前期没用也是以后可以用来对比的数据资产。
  从第一天就用结构化 schema 存下来，六个月后复盘时有完整的
  训练数据——不是散落的 JSON 文件 + 记忆拼凑。

最终裁决：
  数据库 MySQL + Tortoise ORM 保留在 V1.0。
  FastAPI REST 层延迟到多服务通信需求出现时激活（P3 待办）。


【第 7 刀】砍 Phase 3 视频生成（MiniMax video-01）
----------------------------------------------------------------
总监切入角度：
  V1.0 要验证的是"深度理解投喂 LLM 能不能产出有转化的脚本内容"，
  不是"AI 生成的视频画面能不能吸引人"。
  文案转化力跟画面是不是 AI 生成的没有关系。
  花大价钱用 AI 生成精美视频，文案稀烂照样三秒划走——
  而且你测完了根本分不清效果好是因为文案好还是画面好，
  两种变量混在一个实验里，数据无法归因。

PM 反击（成立）：
  黄金 30 秒是完播率的关键。静态图片 + TTS → 用户在 3 秒内
  识别为"低质量幻灯片"→ 划走。文案还没来得及被听到。
  在 TikTok 生态里，视觉动态性和文案质量不是两个独立变量——
  视觉是文案的载具，载具不跑，测不出货物好不好。

最终裁决：
  Phase 3 视频生成保留在 V1.0。它是"让文案能被用户接收到"
  的前置条件，不是锦上添花。


【第 8 刀】砍「怎么讲」库的自动计数 + 自动废弃机制
----------------------------------------------------------------
总监切入角度：
  V1.0 总共 15-20 条表达模板，每天 15 条视频。
  usage_count 手写 tally（"正"字计数）在 Notion 里，
  每天结束花 60 秒更新。哪条到 3 次，手动在 JSON 加
  `"deprecated": true`。
  写自动计数逻辑半天，测试半天，这半天拿来写 Notion 模板
  行不行？

PM 反击（部分承认）：
  在 MVP 版本中这个机制确实浪费算力，
  但在工程化场景中高效，选择保留。

总监逼问（时间分配）：
  "V1.0 2 周冲刺里，自动计数排第几？不在前三就没资格进。"

PM 最终裁决：
  把自动计数 + 自动废弃机制移到 V2 版本。
  V1.0 用手动 tally + 手动标记 deprecated。


【第 9 刀】砍 Phase 2 asyncio 异步并发架构
----------------------------------------------------------------
总监切入角度：
  翻译 + 分镜串行 = 每条多等 2-3 秒。15 条 × 3 秒 = 多等 45 秒/天。
  花一天写 asyncio 并发代码 + 异常处理 + 同步包装，省了每天 45 秒。
  串行给安全扫描留出了天然插入点，不需要额外回调逻辑。

PM 反击（成立）：
  流式输出不仅能节省时间，还能确保准确性。
  翻译通道吐出第一段中间结果时，运营能实时看到。
  如果方向歪了可以提前中断——这不是性能优化，是质量控制的实时性。
  把"事后审核"变成了"实时盯盘"。

最终裁决：
  Phase 2 asyncio 并发保留在 V1.0。
  价值不是省时间，是流式输出的质量控制实时性。

================================================================
四、MVP 核心假设与验证目标
================================================================

核心假设：
  深度理解（人读一本书 → 投喂「讲什么」库）
  + 表达模板（人刷 TikTok → 投喂「怎么讲」库）
  → LLM 生成脚本
  → 能产出有完播率、有互动、有转化的内容

MVP 规模：
  - 3 本书（不同品类，覆盖面够宽）
  - 5 个测试号
  - 日产 10-15 条
  - 周期：跑满 3 周出数据

验证成功的信号（不需要看板，PM 每天刷一眼）：
  - 某条视频完播率 > 30% 且平均观看 > 15 秒
  - 某条视频日均涨粉从个位数跳到 10+
  - 有一条自然评论不是骂我们"广告矩阵"

验证失败的条件：
  - 3 周后 5 个号全无起色
  - 所有视频完播率 < 15%
  - 评论区出现"广告矩阵别上当"

================================================================
六、核心结论
================================================================

1. MVP 的唯一目标是验证核心假设
   → "深度理解投喂 LLM 产生的脚本能不能转化"
   → 所有不直接服务于这个验证的功能，砍。

2. 生产线级别的重型武器不适用于测试阶段
   → 安全用 Excel，去重用肉眼，装配用剪映，数据用人看。
   → 不是因为自动化不好——是因为 MVP 不值得。

3. "数据资产从现在开始积累"是唯一成立的保留理由
   → 数据库从 V1.0 就用，不为 MVP，为六个月后的复盘。

4. 每个被砍功能都有白纸黑字的复活触发条件
   → 不是"以后再做"，是具体数字阈值。
   → PM 不需要靠记忆判断"什么时候该加"。

5. MVP 的 V1.0 PRD 砍到最简骨架：
   → 双 RAG 库 + Phase 1-3（含视频生成 + 异步并发）+ 时间轴对齐
   + 静态安全审核 + MySQL
   → 砍掉自动计数、全自动装配、加密阀门、去重、数据采集、FastAPI

6. 节省的开发时间 ≈ 4-6 周
   → 这 4-6 周全部投入到核心假设验证：3 本书跑通 3 周出数据。

7. Day 2 关键分辨力考验：
   → 自动计数 vs 异步并发，都面临"MVP 量级不够"的砍刀
   → 自动计数砍掉：量级不够 + 手动的 60 秒/天 < 开发半天
   → 异步并发保留：不是省时间，是流式输出的质量控制实时性
   → PM 不能"量级论"砍左边、"未来论"保右边——两个都要具体评估


================================================================
附：推演方法论
================================================================

本次推演采用"铁血敏捷·逐刀砍功能"方法：
  - 每轮指定一个功能，要求 PM 证明它必须在 V1.0 存在
  - PM 防守成功（给出合理理由）→ 功能保留
  - PM 防守失败（无法证明与核心假设验证的关系）→ 砍掉
  - 砍掉后必须给出 MVP 级别的零成本替代方案（SOP/人肉/白牌工具）
  - 每个被砍功能必须记录复活触发条件（具体数字阈值，不是"以后"）
  - 重复九轮（Day 1 六刀 + Day 2 三刀），直到 V1.0 PRD 只剩下骨架

本次与前四个阶段的关联：
  - P1-P4 定义了"完整的房子长什么样"
  - P5 定义了"MVP 只要地基 + 承重墙 + 一个能住人的房间"
  - 其余房间的门牌号写好了，钥匙留好了，等入住率达标再装修
