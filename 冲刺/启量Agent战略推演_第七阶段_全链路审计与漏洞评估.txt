一、推演主题与核心问题
================================================================

本次推演是对过去 8 天（P1-P6）全部推演结论的逐层审计。

审计方法论：
  以"真实出海业务落地"为唯一检验标准，
  抛开代码细节，从全链路商业闭环的角度，
  逐层扫描每个环节是否存在"自以为完美、但真实跑通时
  会立刻导致数据断层或业务停滞"的隐性漏洞。

  每个被发现的漏洞，PM 必须给出闭环方案。
  如果方案成立 → 漏洞消除，审计通过。
  如果方案不成立 → 记录为阶段一残留风险，进入阶段二待办。

审计范围：
  采集层 → RAG 库 → 生成管线 → 安全审核 → 发布 → 用户 → 转化归因 → RAG 反馈


================================================================
二、审计路径回顾（逐层扫描）
================================================================

【审计点 1】转化归因黑域：从完播率到入账之间的断层
----------------------------------------------------------------
审计官发现：
  P1-P6 的全部推演集中在"从书到视频"。
  V1.0 的三个验证成功信号（完播率 > 30%、日均涨粉 10+、
  无用户骂广告矩阵）全部是过程指标，没有一个跟"转化"
  有直接因果关系。

  管线上游设计到了 Phase 4 时间轴对齐，但管线下游——
  从"视频最后一帧"到"用户付款成功"之间——是黑域。

  Phase N（转化与归因）不存在：
    ① 转化入口：视频结尾引导什么？TikTok Shop 购物车？
       多个号是否共用同一个链接、触发平台商业矩阵判定？
    ② 归因链路：怎么知道这条视频卖了几本书？
       TikTok Shop 归因粒度是否到单视频维度？
    ③ 闭环定义：三周后如果数据漂亮但入账为零，
       MVP 验证算成功还是失败？

审计拷问：
  TikTok Shop 后台归因粒度，能不能做到
  "单条视频 → 单品订单数"的归因？

PM 回应：
  TikTok 后台能看到哪一个视频卖的书多。
  → 归因粒度可到单视频 × 单品。

裁决：✓ 闭环。
  RAG 入库标准从"这条火了"升级为"这条卖货了"。
  流量型爆款和转化型爆款被区分开。
  转化归因的黑域被照亮。


【审计点 2】账号人设矩阵的幽灵同源问题
----------------------------------------------------------------
审计官发现：
  45 个号的内容做了三层防同质化（三次即弃、Embedding 去重、
  表达模板分离），但账号层面完全裸奔：

  - 所有号的 Bio 都是"每天推荐一本好书"
  - 头像都是书本封面
  - 受众标签重叠
  - 发布时段高度一致

  TikTok 风控是双层聚类——内容层 + 账号层。
  内容层的所有防护在账号层被一个同源指纹全部击穿。
  这是整个系统最大的单点暴露面。

审计拷问：
  V1.0 5 个测试号的账号人设是什么？
  上线前是否设计好了差异化的人设矩阵？

PM 回应：
  在 RAG 去重位置加账号隔离——「怎么讲」库检索时
  增加 account_persona_id filter。
  每个号只能捞和自己人设匹配的模板。
  五个账号 = 五个 filter = 五种互不重叠的内容风格。


【审计点 3】账号人设的演化 vs 收敛风险
----------------------------------------------------------------
审计官追一层：
  账号人设是预设死还是随数据演化？

  - 预设死 → 某个人设跑两周 0 转化，沉到底
  - 随数据演化 → 运营把不出单的号全调到出单 filter 上，
    45 个号慢慢收敛到 2-3 个出单风格 → 重新制造聚类风险

审计拷问：
  谁定义 persona filter？能改吗？改了之后谁来保证
  45 个号不会在三周后收敛成同一套 filter？

PM 回应：
  允许演化，但主标签锁死 + 子标签演化。
  主标签定死后其他账号不可越界使用别的账号主标签下的模板。
  每个账号在主标签基础上演化子标签。

裁决：✓ 闭环。
  主标签锁死 → 账号间硬隔离，运营无法跨人设调用模板。
  子标签演化 → 数据驱动优化但不越界。
  账号层护城河 = 内容层护城河同级强度。


【审计点 4】发布环节：从文件导出到 TikTok 服务器的真空
----------------------------------------------------------------
审计官发现：
  整条链路管到"视频文件躺在磁盘上"就停了。
  发布时的标题、话题标签、发布时段、上传来源 IP——
  这四个维度的指纹如果重叠，内容的防聚类努力在发布层一秒破功。

审计拷问：
  发布环节有没有操作规范？
  手动发 → 标题/标签/时段/IP 隔离 SOP 在哪？
  API 发 → TikTok 官方 API 允许多账号管理吗？频率限制呢？

PM 回应：
  JSON 格式导入剪映，手动发布。
  Agent 只提供从方案到视频文件，发布动作属于人工 SOP，
  不在 Agent 管线内。

审计官反思：
  这刀砍错了。P5 MVP 裁剪时已确定：
  Phase 4 产出时间轴对齐后的素材包，
  运营手动剪映装配 + 手动发布。
  标题/标签/时段/IP 隔离 → 运营 SOP 层面的事，
  不属于 Agent 管线的工程范畴。

裁决：边界清晰，非漏洞。
  Agent 职责边界 = 从书到视频文件。发布属于人工执行层。

附：审计方法论
================================================================

本次审计采用"黑域扫描法"：
  - 把全链路每个环节的输出和下一个环节的输入一一对应
  - 查找"输出到了但输入没接上"的断点
  - 不预设结论，不讨论"以后可以补"，只找"当前是否通"
  - 发现了漏洞 → 要求 PM 给出闭环方案
  - PM 方案成立 → 漏洞消除
  - PM 无法闭环 → 记录为残留风险

审计视角的特殊性：
  与传统代码审查不同，本次审计不关心代码实现的质量，
  只关心"逻辑上这条链路到底通不通"。
  一条链路如果输出是完播率但需要的是订单数，
  代码写得再好也是断的。
